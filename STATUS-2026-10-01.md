## 3. Bugs found and fixed during testing

These were found by testing, not by reading code. Three of them were **my own** or would have
silently corrupted data:

1. **Silent batch loss (data-loss).** The model always returns `calendarId: "cal_ai_batch"`, and
   the insert used `ON CONFLICT DO NOTHING` — so every batch after the first was discarded while
   the API still reported `persisted: true`. The DB kept the old coffee content while new image
   files overwrote the old ones in place. Fixed with a server-minted unique id per generation.
2. **`public/` is snapshotted at server start.** Images written after boot returned 404, because
   `next start` collects the public file list once. Generated media moved to `media/` (gitignored
   runtime data) and is streamed by `/api/media/[...path]`.
3. **Scheduler could never authenticate.** Middleware redirected `/api/scheduler` and `/api/media`
   to the login page. Both are now self-authenticating (own checks inside the route).
4. **Postgres type error.** Reusing `$1` in both `SET status = $1` and
   `CASE WHEN $1 = 'PUBLISHED'` → *"inconsistent types deduced for parameter $1"* (HTTP 500).
5. **`.gitignore` didn't actually cover media.** My first check matched `/tmp-media/` — a false
   positive. Verified again after fixing.
6. **`test_auth_matrix.js` certified the backdoor.** It asserted that `admin123` returns 200 and
   that the session is an unsigned cookie. Deleted and replaced (§6).

## Round 3 - LinkedIn images actually post, and the post editor is real

### The bug

A post dispatched to LinkedIn came out as text only. Our database had an image for it; LinkedIn never
saw one. Cause: `publishLinkedIn` posted to the deprecated `/v2/ugcPosts` endpoint with
`shareMediaCategory: 'NONE'` and never uploaded the image - and it reported `PUBLISHED` with a reason
that admitted "text only", which is exactly the kind of quiet downgrade that looks like success.

### The fix

`src/lib/linkedin.ts` implements the real flow, and a post with an image never degrades silently:

1. `POST /rest/images?action=initializeUpload` with the author URN -> `uploadUrl` + `urn:li:image:...`
2. `PUT <uploadUrl>` with the file bytes
3. `POST /rest/posts` with `content.media.id` (and alt text)

All calls carry `LinkedIn-Version` (overridable via `LINKEDIN_API_VERSION`, default 202608) and
`X-Restli-Protocol-Version: 2.0.0`. If the image upload fails, the dispatch **FAILS** with the
provider's reason instead of posting text. Text-only posts now also go through `/rest/posts`, so the
deprecated endpoint is gone.

**Verified against live LinkedIn** (the owner's connected account, posts forced to DRAFT via the
documented `LINKEDIN_POST_AS_DRAFT` switch so nothing reached the feed):

- image post: `created as a LinkedIn DRAFT ..., id urn:li:share:7511399438054060032, image urn:li:image:D5610AQEqV-gq5m2-Og attached`
- text post: `... no image`
- with an image AND a mention: `... image urn:li:image:D5610AQGNRmwEWJOzuA attached`
- a draft is reported as SKIPPED, never PUBLISHED, and the row keeps its prior status

### The post editor (modal)

`Edit` on any post now opens `PostEditorModal`:

| Feature | Endpoint | Verified |
|---|---|---|
| Edit copy, live char counter against the platform limit | `PATCH /api/calendar/posts` | counter `340/2200` in the browser |
| Regenerate content for that platform | `POST /api/calendar/posts/regenerate` (target `content`) | 765 chars from deepseek, saved |
| Suggest hashtags (click to add/remove) | same, target `hashtags` | 8 suggestions, note in the UI |
| Regenerate image at the exact platform size | same, target `image` | 1080x1350, 1.67 MB, `resized: true`, served 200 |
| Upload an image | `POST /api/calendar/posts/upload` | PNG accepted and saved; WebP refused `400` with the reason |
| Tag people | `POST /api/linkedin/resolve-tag` | URN and raw id resolve; vanity URL refused with an explanation; invalid URNs are dropped server-side |
| Schedule time | `PATCH` | saved |

Image regeneration runs through the same generator a batch uses (`tools/generate_calendar.py
--singleImage`), so platform sizes, quality and the resize step cannot drift between the two paths.

Access: all three new endpoints return `401` anonymously and `404` for another user's post.

### Honest limits

1. **Mentions only render for 1st-degree connections.** LinkedIn has no public member-lookup API, so
   the id must be pasted (a `/in/name` vanity URL carries no id).
2. **The already-published text-only post cannot be retro-fixed** - the image would have to go out as a
   new post.
3. X and Instagram publishing is still unimplemented (honest `FAILED`, no credentials).

## Round 4 - Dispatch Now asks first, and does not eat the schedule

Two things the owner asked for: a manual dispatch should ask before it posts, and a post that was
dispatched manually must still be published when its scheduled time arrives.

### Confirmation

`Dispatch Now` opens a dialog before anything leaves the machine. It states what will actually happen,
taken from the real connection state rather than an assumption:

| Situation | What the dialog says |
|---|---|
| LinkedIn, live account | "This goes straight to your connected LINKEDIN account (@jmsobin@gmail.com). It cannot be undone from here." |
| X / Instagram, no account | amber - "No INSTAGRAM account is connected, and INSTAGRAM is not configured yet (set INSTAGRAM_APP_ID / INSTAGRAM_APP_SECRET in .env). Dispatching will fail with \"no INSTAGRAM account connected\"." |
| sandbox account only | "The ... account here is a sandbox demo account, not a real one. A dispatch will not reach ..." |

It also lists the scheduled time, whether the post has an image, and how many mentions it carries.

### The schedule survives a manual dispatch

A manual dispatch posts now **and leaves the post queued**, so the scheduler posts it again at its
scheduled time. `keepScheduled` defaults to true; unchecking the box posts once and takes the post out
of the schedule, and the dialog's wording changes to match the box.

Implemented as: the post keeps its `APPROVED` status (the scheduler's own candidate query is unchanged,
which is why the repeat happens), while the manual object is recorded separately in
`manual_published_at` / `manual_external_url` so the manual post and the scheduled post never overwrite
each other. Two guards:

- a post whose scheduled moment has **already passed** is never requeued (that would make the next tick
  repost it in a loop);
- a draft or a refusal never takes a post out of the schedule.

`accepted` (the platform created an object) is tracked apart from `publiclyPosted` (it is visible), so a
draft is recorded without ever being reported as published.

### Verified

| Check | Result |
|---|---|
| Manual dispatch, schedule kept | status stays `APPROVED`, `willPostAgainAt` = the scheduled time, manual post recorded |
| Scheduler still sees it | still a candidate, not yet due |
| Scheduled time arrives | tick picks it up: `publish_attempts` 1 -> 2, a second post created and attached image |
| "post once" branch (SQL) | `PUBLISHED`, `published_at` set, `external_id`/`external_url` set, manual post recorded |
| "keep scheduled" branch (SQL) | `APPROVED`, `published_at` untouched, `external_id` untouched, manual post recorded |
| Dialog, LinkedIn | names the connected account |
| Dialog, Instagram/X | amber warning naming the missing env vars |
| Cancel | nothing posted |
| Scheduler tag carry-through | mentions were being dropped on scheduled posts; now passed |

The live-image **public** path is not covered here: verification ran with posts forced to DRAFT
(`LINKEDIN_POST_AS_DRAFT`), so every post created during testing was publicly invisible, and real
publishing is left to the owner.

## Round 5 - a calendar view, and adding a post to a particular day

### Calendar view

A `View: Day board | Calendar` toggle above the batch. The calendar is a month grid: every day carries
its posts as colour-coded platform chips by status, today is marked, and the chosen month is summarised
(`9 post(s) this month`). Clicking a day opens that day's posts underneath with the same actions the
board offers - Edit (the full editor modal), Approve, Dispatch Now (through the confirmation), Remove -
plus `Add a post on this day`.

Days are grouped by the calendar's own date, and every post is addressed by the id the server stored, so
what you see is what is in the database.

### Adding a post

`POST /api/calendar/posts/create` with `{ calendarId, dayIndex | date, platform, content?, generateContent? }`:

- **The id is minted the way generation mints them** (`post_<calendarId>_<dayIndex>_<platform>`), with an
  `_x2`, `_x3` suffix when that day already has a post on that platform, so a second post on the same day
  never collides with the first.
- **The scheduled slot is the platform's** (X 14:00, LinkedIn 15:00, Instagram 18:00 UTC on that date)
  unless an explicit `scheduledTime` is sent.
- **A date outside the batch becomes a real day**: it is appended to `days_json` with its date, so the
  calendar and the board both show it.
- **Copy is optional**: "write the copy for me" generates it for that platform and tone; unticked, an
  empty post is created for you to write in the editor.
- A date in the past is allowed but flagged in the response: `That time has already passed, so it counts
  as due right now.`

`DELETE /api/calendar/posts?postId=` removes a post, and refuses a `PUBLISHED` one with `409` - deleting
the row would not remove anything from the platform, and the row is the only record that it went out.

### A real bug behind this: the model was choosing the dates

The generated calendar of 1 October 2026 had its days in **April 2025**. The dates and times came
straight from the model's JSON (`scheduledTime` was stored verbatim), so the whole batch was in the past
and the scheduler considered five posts permanently overdue. Dates are now the server's decision: day 1
is tomorrow, consecutive days follow, and each platform keeps its own slot. Verified by generating a
fresh 1-day batch - `day 1 date 2026-10-02`, slots `14:00 / 15:00 / 18:00Z`, `any post in the past: 0`.

The existing calendar has been re-anchored the same way (day 1 -> tomorrow, 543 days forward, 9 posts
moved, times of day preserved). `publishedAt`, `externalUrl` and the manual-post fields were untouched,
so the record of what actually went out is intact. The pre-change data is backed up in
`.tmp/calendar-dates-backup.json` (gitignored).

### Round 5b - creating a post from the calendar itself

- a **`+ New post`** button in the calendar header, opening the dialog on the selected day (or today);
- a **`+`** on every day cell in the grid, opening the same dialog pre-filled with that date and selecting
