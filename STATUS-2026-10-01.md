## 3. Bugs found and fixed during testing

These were found by testing, not by reading code. Three of them were **my own** or would have
silently corrupted data:

1. **Silent batch loss (data-loss).** The model always returns `calendarId: "cal_ai_batch"`, and
   the insert used `ON CONFLICT DO NOTHING` — so every batch after the first was discarded while
   the API still reported `persisted: true`. The DB kept the old coffee content while new image
   files overwrote the old ones in place. Fixed with a server-minted unique id per generation.
2. **`public/` is snapshotted at server start.** Images written after boot returned 404, because
   `next start` collects the public file list once. Generated media moved to `media/` (gitignored
   runtime data) and is streamed by `/api/media/[...path]`.
3. **Scheduler could never authenticate.** Middleware redirected `/api/scheduler` and `/api/media`
   to the login page. Both are now self-authenticating (own checks inside the route).
4. **Postgres type error.** Reusing `$1` in both `SET status = $1` and
   `CASE WHEN $1 = 'PUBLISHED'` → *"inconsistent types deduced for parameter $1"* (HTTP 500).
5. **`.gitignore` didn't actually cover media.** My first check matched `/tmp-media/` — a false
   positive. Verified again after fixing.
6. **`test_auth_matrix.js` certified the backdoor.** It asserted that `admin123` returns 200 and
   that the session is an unsigned cookie. Deleted and replaced (§6).

## 7. Known limitations (stated plainly)

- **Live publishing: LinkedIn only, text-only.** Image upload needs LinkedIn's assets API and an
  approved app. X and Instagram live publishing are not implemented and say so.
- **Instagram identity** resolves the Facebook user; publishing needs the IG business account id,
  which is not wired yet.
- **Text inside generated images is unreliable** (a flowchart came back with "IND" instead of
  "NO"/"END"). Prompt-side mitigation, not fixed.
- **Two writers on one repo.** `start_server.js` was modified by something else again during this
  session, and a foreign process took port 3000 once. Antigravity should be paused while one of us
  edits, or the repo should be handed to one writer at a time.
- **`src/app/page.tsx` still has a display-only `INITIAL_USER` constant** (`usr_creator_01`) used
  as the default UI identity before the session loads. It no longer writes to the DB, but it should
  be replaced with the session user.
- **Costs:** image generation spends real money on your OpenAI key (~$0.01/image at `quality: low`).
  This session's tests generated 9 images.

## Round 2 - the review loop is now real (approval persistence, publishing gate, per-user settings)

The first round made generation/persistence/scheduling honest. This round closes the review loop,
which was still simulated in the browser.

### What was broken

| # | Defect | Consequence |
|---|--------|-------------|
| 1 | `handleUpdatePost` / `handleApproveBatch` mutated React state only | Approving toasted "approved & queued for automated publishing" but wrote nothing. A reload reverted every post to `PENDING_APPROVAL`, so the scheduler could never see an approval. |
| 2 | `handlePublishSinglePost` invented `https://<platform>.com/mock_post` | A fabricated publish URL shown as success. |
| 3 | `handleToggleConnect` disconnect flipped local state only | "Disconnected TWITTER" while the row stayed `connected = true`. |
| 4 | Connections were never read from the database | The studio guessed connection state. |
| 5 | Hardcoded `SANDBOX` badge on every channel | A live connection would still be labelled sandbox. |
| 6 | `/api/media/*` served any generated file to any signed-in user | Cross-tenant read of another creator's content. |
| 7 | `INITIAL_USER` display constant ("Jane Creator") | Studio identity was not the session's. |
| 8 | Middleware exempted any path containing a dot, and redirected API calls to HTML | `/api/media` passed the gate by accident; API clients got a 307 to a login page instead of a status code. |

### What changed

- **`/api/calendar/posts`** (new): `PATCH` one post's `status` / `content` / `scheduledTime`, `POST` to approve a whole calendar. Ownership-scoped: a post belonging to another user or calendar returns 404, and it never leaks whether the row exists.
- **`/api/calendar/latest`** now serves the `posts` table as the source of truth, overlaid on the generation snapshot for day/theme structure. `days_json` is only a snapshot and goes stale the moment anyone approves, edits or publishes.
- **Server-assigned post ids**: the model's ids (`p1_tw`) are rewritten to the stored row ids (`post_<calendarId>_<day>_<platform>`) before persisting, so a UI action addresses a real row.
- **`PUBLISHING_ENABLED`** (new, absent = off): the scheduler refuses to post for real while it is off, records the reason, and leaves the post queued so it retries. `Dispatch Now` is an explicit human action and still posts per post. Verified with a live (non-sandbox) connection row: the scheduler answered `SKIPPED - live publishing is OFF ... Use Dispatch Now to post this one explicitly`.
- **`/api/settings`** (new): image quality (`low` / `medium` / `high`) persisted per user and used by the next generation; the studio shows the knob with its per-image cost and the live-publishing state.
- **`/api/social/connections`** (new): `GET` returns real connection state; `DELETE` revokes the token and reports `wasConnected` honestly.
- **`/api/social/platforms`** (new): which platforms have credentials, so unconfigured channels show `NOT CONFIGURED` instead of a Connect button that cannot work.
- **`/api/media/[...path]`**: now requires the requesting user to own the calendar the media belongs to.
- **Middleware**: real static-extension allowlist; API routes answer `401 {"error":"Not authenticated"}` instead of redirecting to an HTML login page.
